**GLM-4.7-Flash + llama.cpp (collected issues, refs: Reddit, llama.cpp #18835 #19068 #19128, PR #18980):**
- **MoE gating (sigmoid vs softmax):** FIXED in llama.cpp Jan 21 2026 (PR #18980). GLM-4.7-Flash uses sigmoid for expert gating; wrong gating caused looping and poor output. Use a build that includes this fix (our `external/llama.cpp` does) and re-download Unsloth GGUF (they added `scoring_func: sigmoid` to config).
- **Gibberish with Flash Attention + cache-reuse:** With `--flash-attn on` and `--cache-reuse`, 2nd/3rd prompt can produce garbage once context reaches several thousand tokens. **Workaround:** do not use `--cache-reuse` with GLM. Our `run_server.sh` does not pass `--cache-reuse`, so we are safe.
- **Vulkan regression (since b7667):** On Vulkan backend, longer prompts can produce repeating Chinese/symbols; CUDA works. We use CUDA build only; avoid Vulkan for GLM.
- **Grammar / tool-calling corrupted state ("Grammar still awaiting trigger"):** See detailed subsection below.
- **High CPU with CUDA:** Some users report high CPU when using CUDA for GLM; trying `--flash-attn off` and `cache-type-k/cache-type-v bf16` (and smaller context) has been reported to move more work to GPU. Optional to try if CPU is saturated.

**GLM "Grammar still awaiting trigger" – why it happens, context, why not fixed yet**

- **What it is:** When the client sends a request with **tools** (OpenAI-compatible, e.g. Cursor/OpenCode with tool definitions), llama-server uses a **lazy grammar**: it generates tokens freely until the model outputs a **trigger** (e.g. for GLM the trigger is `\n<tool_call>`). Only then does it apply a strict grammar so the rest of the output is valid XML tool-call format. The log line "Grammar still awaiting trigger after token X (`y`)" means: we're in that lazy state and the last token wasn't the trigger, so the server keeps generating without applying the grammar.

- **In what context it happens:** (1) **Tool-calling requests** – client sends `tools` (and often `tool_choice: "auto"`). (2) **GLM 4.5 format** – server expects the model to eventually emit `\n<tool_call>` so the grammar can kick in. (3) **Long generations** – if the model never emits that exact trigger (e.g. it keeps answering in plain text, or emits something slightly different), the server keeps generating up to `max_tokens`. During that time it appends every generated piece to an internal **trigger buffer** and logs "Grammar still awaiting trigger" for each token.

- **Why the corrupted state / gibberish:** In reported cases (llama.cpp #19068), after the server has been in "awaiting trigger" for a long time (e.g. 25k+ tokens, `n_remaining` in the tens of thousands), it can enter a **corrupted state**: the next request returns **gibberish from the first token** and CPU RAM grows to ~8× normal (memory leak). Likely causes: (a) **Unbounded trigger buffer** – while awaiting trigger, the grammar code appends each token's text to `trigger_buffer` and keeps `trigger_buffer_positions`; for 60k+ tokens that can blow memory and possibly corrupt state if not reset properly between requests. (b) **Slot/grammar state not fully reset** when a request ends without the trigger ever firing, so the next request reuses a bad state. (c) **Malformed prompts** (e.g. two consecutive user messages without assistant reply) may leave conversation or grammar state in an odd shape. (d) **Trigger tokenization mismatch** – if the model's vocab tokenizes `<tool_call>` differently than the server's preserved token, the trigger might never match; the server would then run in "awaiting trigger" until max_tokens, amplifying (a)–(b).

- **Why it's not fixed yet:** (1) **Intermittent** – no reliable repro; happens "after hours" or with specific tool/prompt patterns. (2) **No root-cause fix in tree** – issue #19068 is open; no PR that limits trigger buffer, adds a timeout, or forces a full grammar/slot reset after N tokens without trigger. (3) **Related fix (#15608)** – a *crash* when a newline appeared before the tool_call token was fixed (empty grammar stack); that's a different bug (crash vs. infinite loop + corruption). (4) **Mitigations you can do:** Restart the server when you see gibberish or huge RAM. Prefer **tool_choice: "required"** when you know you want a tool call (triggers grammar immediately, no lazy wait). Limit **max_tokens** for tool requests so "awaiting trigger" runs for fewer tokens. Avoid malformed conversation shapes (e.g. two user messages in a row without assistant). If you don't need tool calling for a run, use a request without `tools` so no grammar is used.

**Qwen3-Coder re-reads same file chunks (known upstream):** Model repeatedly re-reads the same file (e.g. 20+ times on a 1000-line file) instead of moving on. Reported as model/training issue; also related to tool_choice "auto" vs "required" and parser behavior. See: [QwenLM/qwen-code#66](https://github.com/QwenLM/qwen-code/issues/66), [QwenLM/Qwen3-Coder#480](https://github.com/QwenLM/Qwen3-Coder/issues/480). Workarounds: try tool_choice "required" where possible; limit file/chunk size; or use another model for file-heavy tasks.
